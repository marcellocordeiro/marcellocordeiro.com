## Background

When I was close to graduating from university all that was left was an internship. So I did a short stint at a local startup. I had no prior experience with web or mobile development, and their stack comprised of:

1. A dashboard written in pure HTML, JavaScript and CSS
2. Two multiplatform mobile apps written in React Native
3. A few embedded system firmwares for the ESP8266, written in C++, using the MQTT protocol for uploading data into a Firebase database

I had no trouble picking up 3., as I had a reasonable amount of C++ and systems programming experience under my belt from writing CHIP-8 and NES emulators. I had _heard_ of React Native before, or rather just that React was the hottness at the time, but learning the frameworks and upgrading the mobile apps to modern React Native using the latest libraries and TypeScript was engaging and fun. When it was time to do maintenance on the dashboard I felt it was going to be a different story, because the website's code had a ton of raw HTML injected by the JavaScript code, and those patterns went completely against what I expected coming from React Native.

I had a plan though. I was young and naive, so I did the most reasonable thing anyone in my shoes would also do: I learnt about bundling with Webpack, injecting small islands of React code (in the most dynamic and _reactive_ parts), until I realised I was ready to rewrite the whole thing using React and the Vite framework. And so I did. I reused the mix of Bootstrap with custom CSS, sprinkled a little bit of Tailwind CSS, rewrote the whole code in TypeScript, and did my best to apply the best modern React and state managing patterns.

The results were staggering: no more 4-5 second delay when navigating between pages due to the whole JavaScript code having to start from the scratch, instant navigations, several bugs, both tracked and untracked, were fixed, and we were able to share a fair amount of code with the mobile apps.

So, that's what I've known for years. Even after landing a new job I kept up with the web dev scene: I learnt about Next.js, static site generation, server rendering, single/multi page applications (SPA/MPA) and their trade-offs, and a whole bunch of other stuff ~~(i.e., I don't remember)~~. I could always write the code, but designing interfaces off the top of my head was the real final boss.

## The Stack

### First experiment

Fast forward a few years, I yolo-ed and bought this domain. I was dedicated to writing the website from the scratch. I knew Next.js and I knew it supported MDX. The stack was supposed to be a no-brainer:

1. Framework: Next.js
2. UI framework: Mantine
3. Articles: MDX

What could go wrong? Well, first of all, I'm _still_ no designer, so I was having a lot of trouble coming up with a design I wanted, especially after looking into dozens of portfolios and blogs, and I was never happy with whatever I'd came up with. Second, making Next.js generate static pages in `{ output: "static" }` mode was difficult if I wanted to maintain a good developer experience, due to limitations from having to go "against the grain". DX is incredibly important to me because I enjoy building solid foundations to avoid having headaches or too much manual labour when iterating over it.

Unfortunately, I lost the code I had to use when gluing the Markdown file discovery with Next.js' `generateStaticParams()`. It originally used Node.js file system functions with globs with `remark-frontmatter` + `remark-mdx-frontmatter` or `gray-matter` to parse and export the frontmatter (basically, the metadata of the Markdown file, including title, slug, description, publication date, etc...)

The page itself looked a bit like this:

```tsx
type Props = PageProps<"/blog/[slug]">;

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params;
  const post = getBlogPost(slug);

  if (!post) {
    notFound();
  }

  return {
    title: post.title,
  };
}

export default async function Page({ params }: Props) {
  const { slug } = await params;
  const post = getBlogPost(slug);

  if (!post) {
    notFound();
  }

  const { Content } = post;

  return <Content />;
}

export function generateStaticParams() {
  return getBlogPostsSlugs();
}
```

Not bad. But, behind `getBlogPostsSlugs()`, there was a lot of annoyances and boilerplace. Oh, and there was no styling yet. I didn't feel happy with Mantine (100% my fault).

### Second experiment

Clearly, I was unhappy with how things were working. Therefore, I did a lot of research and came up with this:

1. Framework: Next.js
2. UI "framework": Tailwind CSS + Tailwind CSS Typography + shadcn-ui
3. Articles: MDX
4. Content collection: Content Collections (`content-collections`), from `content-collections`

Content Collections was a rare find, because Contentlayer was traditionally recommended as the data layer, but it's unmaintained so Velite came as an alternative, however, it had some issues with Turbopack and it didn't feel ergonomic to use. Maybe it's better now though. The `content-collections.ts` code looked like this:

```ts
import { createDefaultImport, defineCollection, defineConfig } from "@content-collections/core";
import type { MDXContent } from "mdx/types";
import type { StaticImageData } from "next/image";
import { z } from "zod";

const posts = defineCollection({
  name: "posts",
  directory: "src/content/blog",
  include: "**/*.{md,mdx}",
  parser: "frontmatter-only", // Let Next.js' MDX processor do all the content and plugin work
  schema: z.object({
    slug: z.string(),
    title: z.string(),
    description: z.string(),
    date: z.coerce.date(),
    image: z.string(),
    tags: z.array(z.string()).default([]),
    dev: z.boolean().default(false),
  }),
  transform: ({ _meta, ...post }) => {
    const Content = createDefaultImport<MDXContent>(`@/content/blog/${_meta.filePath}`);
    const image = createDefaultImport<StaticImageData>(`@/content/blog/${post.image}`);

    return {
      data: {
        ...post,
        image,
      },
      Content,
    };
  },
});

export default defineConfig({
  content: [posts],
});
```

Pretty cool, huh? It'd handle finding the files, hot-reload, and do the frontmatter parsing and validation. I removed a ton of Node.js code. If you already know where this article is going you might be having déjà vu.

I chose Tailwind CSS over Mantine because it's still the most popular tool for writing UIs, has an excellent documentation, provides the Typography plugin, and shadcn-ui has become even bigger than Tailwind itself. This meant I would have an easier time with this stack since it'd be a lot easier to find examples and prior work, especially for someone who isn't particularly thrilled about CSS.

Great! Everyone is happy, the sun is shining, all the birds are singing. This is looking solid (not to be mistaken with Solid). And then it was time to give the blog posts some flair and add all things you'd expect from a blog post. Any website that's going to talk about code is going to need some syntax highlighting.

Then things started falling apart. There are lots of methods to support syntax hightlighting, both client and server side. I required it to render server side since there was no need to let the client do any work and it could be pre-rendered during build time. After a lot of research around Shiki, Prism, and the Remark/Rehype plugin system, I opted to use `@shikijs/rehype`, a Rehype plugin for Shiki. This worked great! But, again, any website like this one is legally and morally obligated to support dark theme. I used `next-themes` to handle the themes. However, the code blocks would never adjust to the correct theme. After some research and reading the docs (very important), I came up with this:

```ts
const rehypeShikiOptions: RehypeShikiOptions = {
  themes: {
    light: "github-light-default",
    dark: "github-dark-default",
  },
  defaultColor: "light-dark()", // This did the trick
};
```

But, of course, I also needed to support the usual plugins:

```ts
const withMDX = createMDX({
  extension: /\.mdx?$/, // md and mdx
  options: {
    format: "mdx", // Keep html tags in md files
    remarkPlugins: [
      // The two frontmatter plugins were still required
      "remark-frontmatter",
      "remark-mdx-frontmatter",
      "remark-gfm",
      "remark-smartypants",
    ],
    rehypePlugins: [
      "rehype-slug",
      "rehype-mdx-import-media",
      ["@shikijs/rehype", rehypeShikiOptions],
    ],
  },
});
```

This took me a lot of work to come up with. Sure, I want to be meticulous and make the choices count, but I wanted to use as many plugins as possible to cover the basics. For example, `remark-gfm` (GitHub Flavored Markdown) gives you a more GitHub-like flavour, `remark-smartypants` adds support to smart quotes, `rehype-slug` adds `id` attributes to headings so it's possible to use anchor tags to navigate or share a link to them, and `rehype-mdx-import-media` helps with media imports.

Phew. Can't believe it took me this long to learn how much stuff was needed that I took for granted in other websites. Maybe it would've been better to just use a meta-framework or tool like Zola. This came at a time I kept seeing the name Astro come up. It supported everything, the content collections layer, syntax highlighting, all the usual plugins pre-configured, and a method to collect headings to support navigations or table of contents. Some of them didn't even have plugins remark/rehype plugins that worked with the current stack! That brings us to...

## Challenges

Coming from Next.js and React in which they are the bread and butter for most web developers and many features are either given to you or are given a different name sure had a learning curve. But my challenges weren't limited to just the stack changes. I can break them down to a few topics:

- Tooling
- Ecosystem
- Scripting
- Styling
- Theming

### Tooling

This one was a doozy. When dealing with JavaScript/TypeScript you want your code base to follow very strict rules to ensure you're not straying away from the beaten path. React code is just JavaScript with JSX. It's the most popular library out there. I was very excited to see tools like oxlint/oxfmt and Biome, because, let's face it, ESLint is a product of its time. ESLint does not provide an easy way to setup all the necessary plugins, and `typescript-eslint`, albeit very well made and documented, adds a whole other layer of complexity to your ESLint configuration, which in v9 and v10 started forcing the flat-config thus breaking the whole massive ecosystem. Plugins are also mostly maintained by many different third parties, making it easy for them to fall behind major releases.

Astro, however, is written in `.astro` files, basically containing a frontmatter which runs TypeScript code during build time to provide data to the template which is written in JSX, and `<script>` and `<style>` blocks for scripting and styling, respectively. The newer linters and formatters do not yet support Astro files, and at best will only parse the frontmatter.

There isn't a proper solution to this yet, so I've settled with the good old Prettier + official plugin and ESLint with the community maintained plugin for Astro. This works fine, but I'm maintaining my oxlint/oxfmt and Biome configs to jump ship as soon as I'm able to.

Other than linters and formatters, the tooling is solid. I run `astro check && tsc` to validate my Astro files using the official tooling and of course typecheck using TypeScript.

### Ecosystem

The React ecosystem is massive. The community has written (mostly) everything needed for most people to build with. Even shadcn-ui components use unstyled React libraries to provide React components, which thankfully are fully supported by Astro.

Astro's ecosystem is tiny in comparison. Resources are limited, but their docs are excellent. I had originally opted into using shadcn-ui's React components, but since I was using Astro and it steers you into writing HTML + TypeScript the old fashioned way I thought it was a good opportunity to learn something new that would be a better fit for my website, since most of it doesn't require much interactivity.

### Scripting

Okay, I need to get something out of the way first. At the time of writing this article, the only two interactive components are the button for the mobile navigation and the theme selection buttons for dark mode. For interactive components I actually opted into learning Svelte and rewritting the shadcn-ui React components in Svelte. Svelte was interesting because it compiles into much smaller code and handles state in a simpler way, but not without some potential footguns. I'll talk about it more in detail in the theming section, but after a while I opted back into React to avoid maintaining code I never wrote in the first place.

I'm the kind of person who may struggle a bit getting stuck with something I'm not 100% on board with, until I randomly stumble upon something cool and suddenly I'm **invested**. I found about Web Components from the Astro docs and simpler ways to handle my website's header, so I decided to port the shadcn-ui Tailwind classes to Astro components and remove as many dependencies and code from the bundle as possible. This was very cool, as it allowed me to write interactive code in a decent way without using any dependencies.

### Theming

This part took me very long to settle and caused me to shift between UI libraries the most. Supporting dark mode is non-negotiable to me, but I didn't want to just drop a toggle between light and dark, the plan was to support light and dark mode or match the system's theme. This meant keeping consistency with the local storage preference as well, meaning `system` should in fact clear the preference and let the browser figure it out:

| Website | User preference | Result |
| ------- | --------------- | ------ |
| Light   | Any             | Light  |
| Dark    | Any             | Dark   |
| System  | Light           | Light  |
| System  | Dark            | Dark   |

You can test this yourself, by either changing your system preference or going into your browser's dev tools and simulating light or dark mode.

The hardest part of this was avoiding a FOUC (Flash of Unstyled Content), which would manifest when forcing the theme to a value different from the system and refreshing the page. It's possible to read the user preference when rendering the theme selector in the client, but by the time the script loads I'll have my readers flashbanged and that wouldn't be nice. I've looked into shadcn-ui's docs for dark mode but I felt I could do better, and it didn't work well with View Transitions. So after reading the Astro docs and looking into `next-themes` I came up with this:

```astro
<script is:inline>
  function applyTheme() {
    let theme = localStorage.getItem("theme");

    if (theme !== "light" && theme !== "dark") {
      theme = matchMedia("(prefers-color-scheme: dark)").matches
        ? "dark"
        : "light";
    }

    document.documentElement.dataset.theme = theme;
  }

  document.addEventListener("astro:after-swap", applyTheme);
  applyTheme();
</script>
```

Since Astro's inline scripts are unprocessed, I couldn't import my reusable theme helpers, but this was pretty good to at least sync with the user preference before rendering for the first time.

Now we have to deal with syncing the media query for the user preference when the current theme should follow the system's. I wrote a `.svelte.ts` state manager and it felt very elegant:

```ts
export function createThemeContext() {
  let currentTheme: Theme | null = $state(null);
  const prefersDarkMode = new MediaQuery(DARK_MODE_MEDIA_QUERY);

  // Initial state, only run once
  onMount(() => {
    currentTheme = getSavedTheme() ?? "system";
  });

  // Media query listener
  // Should not update the local storage
  $effect(() => {
    // Make sure this dependency is registered
    // Moving this after the conditional will stop this effect from running
    const theme = prefersDarkMode.current ? "dark" : "light";

    // Only update the DOM if the user did not set any preference
    if (untrack(() => currentTheme) !== "system") {
      return;
    }

    updateDOMTheme(theme);
  });

  function handleUserSelection(value: Theme) {
    currentTheme = value;

    updateTheme(value);
  }

  return {
    get value() {
      return currentTheme;
    },
    apply(value: Theme) {
      if (value === currentTheme) {
        return;
      }

      handleUserSelection(value);
    },
  };
}
```

Compare it with the equivalent React code, which was used after migrating all the code back to React:

```tsx
export function ThemeToggle() {
  const [currentTheme, setCurrentTheme] = useState<Theme | null>(null);

  useEffect(() => {
    // oxlint-disable-next-line react/set-state-in-effect
    setCurrentTheme(getSavedTheme() ?? "system");
  }, []);

  useEffect(() => {
    const mql = globalThis.matchMedia(DARK_MODE_MEDIA_QUERY);

    const onChange = () => {
      // Only update the DOM if the user did not set any preference
      if (currentTheme !== "system") {
        return;
      }

      const theme = mql.matches ? "dark" : "light";

      updateDOMTheme(theme);
    };

    mql.addEventListener("change", onChange);

    return () => mql.removeEventListener("change", onChange);
  }, [currentTheme]);

  const handleThemeChange = (theme: Theme) => {
    setCurrentTheme(theme);
    updateTheme(theme);
  };

  return (
    // UI elements
  );
}
```

The React version isn't bad, but it uses a pattern that isn't recommended to use in hooks. The Svelte version feels nice but at the same time I ran into this footgun where it would ignore the media query if I didn't immediately try to access it before the current theme check.

After discovering Web Components I decided I'd try to replace all of my React code, and this is what I came up with:

```ts
class ThemeToggle extends HTMLElement {
  private mql: MediaQueryList | null = null;
  private onMqlChange = this.handleMediaQueryChange.bind(this);

  private currentTheme: Theme | null = null;

  private buttons: NodeListOf<HTMLButtonElement> | null = null;

  connectedCallback() {
    this.currentTheme = getSavedTheme() ?? "system";
    this.buttons = this.querySelectorAll("button[data-value]");

    this.syncButtons(this.currentTheme);

    this.buttons.forEach((button) => {
      button.addEventListener("click", () => {
        const { value } = button.dataset;

        if (!isTheme(value)) {
          console.warn(`Invalid theme value: ${value}`);
          return;
        }

        this.handleThemeChange(value);
      });
    });

    this.mql = globalThis.matchMedia(DARK_MODE_MEDIA_QUERY);
    this.mql.addEventListener("change", this.onMqlChange);
  }

  disconnectedCallback() {
    this.mql?.removeEventListener("change", this.onMqlChange);
  }

  handleMediaQueryChange() {
    if (!this.mql) {
      console.warn("mql is not initialised.");
      return;
    }

    // Only update the DOM if the user did not set any preference
    if (this.currentTheme !== "system") {
      return;
    }

    const theme = this.mql.matches ? "dark" : "light";

    updateDOMTheme(theme);
  }

  handleThemeChange(selected: Theme) {
    this.currentTheme = selected;
    updateTheme(selected);
    this.syncButtons(selected);
  }

  syncButtons(selected: Theme) {
    this.buttons?.forEach((button) => {
      const { value } = button.dataset;

      button.className = cn(
        buttonVariants({
          variant: value === selected ? "default" : "outline",
          size: "default",
        }),
      );
    });
  }
}
```

It's not perfect, there are probably bugs in it, but it works and doesn't need any UI library! It also allows querying for components only within the Web Component, so no need to write something like `document.querySelectorAll("button[data-value]")` anymore.
